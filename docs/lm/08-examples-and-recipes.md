# Examples and Recipes

This is a catalogue of the worked examples on the original site, grouped by the technique they show. Short rulesets are quoted in full. For longer ones, only the rules that show the technique are quoted. Page names are relative to https://languagemachine.sourceforge.net/.

The repository's `calc.lmn` is a cut-down version of the forward Polish calculator below: it has only `+` and integer numbers. The site gives expected output for most of these examples, so they make good regression cases for the Go port.

## Output and the minimal ruleset

### lmcat (`minimal_rule_set_-_lmcat.html`)

```
   - out <- eof - ;          // compiles to:  m:lm_ L:0 n:1 ( z m:out ) ( m:eof ) r
```

The rule copies input to output. It is always relevant to the goal `eof`, never produces `eof`, and consumes one symbol each time it is applied. When the real `eof` arrives, the goal is matched and the run succeeds. The output section of most rulesets looks like this rule.

## Calculators

### Forward Polish (`guide.html`, `lm-diagram.html`)

See [03-lmn-language.md](03-lmn-language.md#a-complete-example-the-forward-polish-calculator). The factorial extension selects on argument values:

```
'f' x :N  <- x - '*' x :(N) 'f' x :(N - 1) ;
'f' x :1  <- x :1;
'f' x :0  <- x :1;
```

Expected session (`lm -r fpCalc.lmr`):

```
* 100 / 1 3          ->  result: 33.3333
f 6                  ->  result: 720
z                    ->  --- not understood - skipping one line
* 1 + / 1 55 * 3 22  ->  result: 66.0182
```

### Infix with precedence (`calc.html`, `extendcalc.html`)

Operator precedence comes from grammar priorities. A top-down `expr` builds on `opnd op`:

```
 .calc(0B)
  '(' expr :N ')'                      <- opnd:N ;
 .calc()
   - opnd :A op                        <- expr - ;
   -                                   <- op expr:A;
 .calc(10L)
   '+' expr :B                         <- op opnd:(A + B);
   '-' expr :B                         <- op opnd:(A - B);
 .calc(12L)
   '*' expr :B                         <- op opnd:(A * B);
   '/' expr :B                         <- op opnd:(A / B);
 .calc(18L)
   '-' opnd :A                         <- opnd:(- A);
 .calc(20L)
   ' '                                                                                     <- -      ;
   '0'                % { repeat .[0-7]       % } octal yes                       toOct :N <- opnd :N;
   [0-9]              % { repeat .[0-9]       % } { option '.' % repeat [0-9] % } toNum :N <- opnd :N;
   '0x'  .[0-9a-zA-Z] % { repeat .[0-9a-zA-Z] % } { option '.' % repeat [0-9] % } toHex :N <- opnd :N;
   '0b'  .[01]        % { repeat .[01]        % }                                 toBin :N <- opnd :N;
```

In `op opnd:(A + B)`, the `A` is the variable bound by `- opnd :A op` in the enclosing context, which shows cross-context scope. The page's session output is `103+17*3.23-3=` → `the answer is 154.91`. `extendcalc` adds `format(...)`, the `var*` builtins, `trOn`/`trOff` and calls to external C and D procedures.

### Reverse Polish (`rpcalcdiagram.html`)

There is no visible stack: operators find their operands through variables in enclosing contexts.

```
   - rp x :N '='   <- result 'result: ' N '\n' eom ;
   -               <- rp ;
   - x    :A f1 :B <- rp - x  :B ;
   - rp x :B f2 :C <- f1 :C ;
   'N'             <- f1 :(-A);
   '+'             <- f2 :(A + B);
```

## Recursion and backtracking

### Left recursion (`leftrecursive.html`)

```
 - word :X             <- sample - list :X :X;
 list :B :F ';'        <- sample   'here it is forwards:  ' F '\n' 'here it is backwards: ' B '\n'eom;
 list :B :F word   :X  <- sample - list:{ X ', ' B } :{ F ', ' X };
 list :B :F number :X  <- sample - list:{ X ', ' B } :{ F ', ' X };
```

Input `a 1 2 c;` produces forwards `a, 1, 2, c` and backwards `c, 2, 1, a`. The newer `number` rule is tried first, and when it fails the machine backtracks, re-establishing two levels of right nesting. To avoid that backtrack, factor the alternatives into `item`:

```
 - word :X          <- item :X;
 - number :X        <- item :X;
 list :F :B item :X <- sample - list:{ X ', ' B } :{ F ', ' X };
```

### Tail recursion without input (`bottles.html`, `99bottles.html`)

The verses are generated by `thing :N` rules with special cases for 2, 1 and 0:

```
   start var N = 99; <- eof - first :N :"s" thing :N song eof;
   thing :N          <- verse a :N         :"s" b :(N-1)     :"s" eom thing :(N-1);
   thing :0          <- verse a :"No more" :"s" c :A         :T   eom ;
```

This page explains how right-side levels collapse, the "something from nothing" `sync` trick, and why input-free rulesets need `-i dummy`.

## Buffers, tables and reordering

### Reorder lines (`output_buffers.html`)

```
.reorder()
   start var Table = []; eof <- eof - generate
       { for(var I = 0; I < 2; I++) { "\n=== group " I " ===\n" $(Table[I]) }} output eof;
   - pick :X toX                   <- eof - ;
   ' '                             <- pick :0 ' ';
   - terminal :A                   <- pick :1 A  ;
   - (Table[X])                    <- toX - ;
   '\n'                            <- toX - "\n" toX;
   eof                             <- toX - "\n" toX eof;
   generate output                 <- eof   - ;
   - out                           <- output -;
```

### Flattening nested blocks (`flattening_a_nested_structure.html`)

Each `{…}` block is collected into its own buffer `Code[I]` and replaced by a reference `[[#block_N]]`. The blocks are then printed in reverse order.

```
  start var Code = []; var N = 0; var I; analyse <- eof - generate
     { for(I = N; I >= 0; --I) { "\n=== block " I " ===\n" $(Code[I]) '\n' }} output eof;
   -  var I = 0;   flatten     <- analyse;
  '{' var I = ++N; flatten     <- flatten - refA "#block_" I refZ;
   refA                        <- flatten - "[[";
   refZ                        <- flatten - "]]";
  eof                          <- flatten;
  '}'                          <- flatten;
  - (Code[I])                  <- flatten -  ;
   generate output             <- eof   - ;
   - out                       <- output -;
```

The page's input:

```
this is at the the outermost level. { but this is in an { inner } block { as also
is this, only more so }. We're back. }
what happened? { did it work? }
Well?
```

Expected output, from block 4 down to block 0. Blocks 3 and 2 are omitted here.

```
=== block 4 ===
did it work?
…
=== block 1 ===
but this is in an [[#block_2]] block [[#block_3]]. We're back.
=== block 0 ===
this is at the the outermost level. [[#block_1]]
what happened? [[#block_4]]
Well?
```

### Lexical analysis with a symbol table (`lexicalbuffer.html`, `lexicalresults.html`)

This example combines `%` with `(Buffer)`, uses an associative array `Sy` to assign an identity to each unique symbol, handles quotes with full escape sequences, and exercises every conversion builtin.

```
   - ; var J = 0; var Sy = [];   analyse    <- eof - ;
   - if(Sy[V] == "null") Sy[V] = J++;       <- identity:(Sy[V]) ;
```

### Common stems (`stemming.html`, `stemming_experiment.html`)

Associative arrays are used to find common stems, a technique that also applies to finding common subexpressions.

## Context-sensitive and unrestricted grammars

These are covered in `context_sensitive.html`, `context_sensitive2.html` and the pages they link to.

- **`aibjaibj`**, {aⁱbʲaⁱbʲ}: the first half is captured as deferred patterns, which are then required literally.

  ```
     'a'                         <- a :{ a :X };
     - a :A repeat a :A          <- aseq1 :{ each A };
     - aseq1 :A     bseq1 :B     A     B <- success;
  ```
- **`anbncn`**: the "standard" monotone grammar `S: | abc | aSBc. cB: Bc. bB: bb.` translated to lmn. It needs an extra nonterminal `_b` so that recursion gets a chance:

  ```
    -               <-  _S;
    'a' _b  'c'     <-  _S;
    'a' _S  _B 'c'  <-  _S;
    _B  'c'         <- 'c' _B;
    'b' _b          <- _b _B;
    'b'             <- _b;
  ```

  The author's warning: rules that are triggered by a *terminal* as goal are risky unless they really apply wherever that terminal can be the goal.
- **`anbncn_each`**: each `'a'` supplies the recognisers for the corresponding `b` and `c`, which are collected with `each`.
- **`ambnambn`** and **`ambmcmdmem`**: these use no variables. "Driver" nonterminals are generated and permuted by pure rewriting, for example `_a _b <- _b _a ;`.
- **`hippos`**: English, Dutch and German crossed-serial word orders are rewritten into one canonical order. Each noun supplies an on-demand verb recogniser (`require`) that builds forward or reversed lists.

## Lambda calculus (`lambda.html`, `lct.html`, `lcm.html`, `curried_functions.html`)

- `lct` compiles lambda expressions into lmn rules. Bound variables become LM variables prefixed with `V`, and free variables become symbols prefixed with `_`.

  ```
  _reverse3 y :Va y :Vb y :Vc <- r f :_reverse3 :{ Va Vb Vc } :{ Vc Vb Va } ;
  ```
- `lcm` is the runtime that evaluates them. It handles currying by treating missing arguments as empty and emitting `curry`. Each function carries a "bag" of arguments, which works like a closure.
- `lists.lam` and `arithmetic.lam` exercise the system with Church encodings, the Y combinator, map, zip and reverse.
- The experiment shows that the engine contains the lambda calculus and is therefore Turing-complete.
- Run with dummy input, for example `./lists.lm -i z`.

## Translators and tools

| Example | What it is |
| --- | --- |
| `groklm`, `grokout`, `grokreg` (+ `_experiment`) | Expressions and assignments go to an internal prefix form, such as `f2 :add :A :B` or `fa :set :A :B`. Code-generator rules then produce Lisp-style output (`groklm`), a filter that passes through unmatched text (`grokout`), or 3-address code with register allocation (`grokreg`). |
| `grokcpp` | Approximates the C preprocessor's `#include`, `#define` and `#undef`, using a table `D`. |
| `mediawiki`, `sitehtml`, `website` | The rules that generated the site: a MediaWiki subset converted to HTML, with site-specific overrides. |
| `wiki2make`, `testmakefile` | A Makefile written in wiki format and converted to a real Makefile. |
| `d2xfe`, `d2dbe`, `d_to_d_translator` | A D-to-D translator: a complete D frontend plus a backend that regenerates D source. It was tested on DMDScript and on the machine's own sources. |
| `j2d` | A Java-to-D translator adapted from d2d in under two weeks. It parses about 750k lines of Java. |
| `gcc_interface`, `treedef`, `d2gccbe` | Experiments that drive gcc's GENERIC code generator. `treedef` generates D stubs from `tree.def`. |
